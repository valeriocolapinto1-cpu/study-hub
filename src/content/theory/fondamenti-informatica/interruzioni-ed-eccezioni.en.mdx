<Callout tone="ok" title="In two minutes">

<div data-note-id="teoria/interruzioni-ed-eccezioni/in-due-minuti">

- **Interrupt** = external, asynchronous event, unrelated to the current instruction. **Exception** = event generated by the instruction itself (overflow, illegal instruction, page fault).
- Sequence: finish the current instruction → save PC and status → mask interrupts → jump to the **ISR** → return with a dedicated instruction that restores everything.
- **Priority** and **masking** decide who can interrupt whom: nesting is allowed only towards higher priorities.
- Identifying the source: **polling** the status registers (time proportional to the number of devices) or **vectored** interrupts (the device supplies the address of the routine).
- The ISR must save and restore the registers it uses: the interrupted program must not notice anything.

</div>

</Callout>

<div data-note-id="teoria/interruzioni-ed-eccezioni/da-dove-si-parte">

## Where we start

**What you need to know first:** the fetch-decode-execute cycle ([processor](../processore/)) and procedure calls with the stack ([instruction set](../risc-cisc-assembly/)).

**What problem it solves.** The processor executes one instruction after another and never looks outside. But the outside world does not wait: a key is pressed, a packet arrives, a timer expires. How does the processor notice without spending its life checking? The answer is to reverse the direction: it is not the processor that asks, it is the device that **calls**. From here interrupts are born — and the same mechanism also handles the errors an instruction can cause.

**New words.** An **ISR** (Interrupt Service Routine) is the procedure that answers a request. **Masking** an interrupt means temporarily saying “not now”. An interrupt **vector** is the address of the routine to run, supplied by the device itself. **Asynchronous** means “not tied to the current instruction”, **synchronous** the opposite. The **context** is the set of PC, status and registers that allows the interrupted program to resume as if nothing had happened.

</div>

</Layer>

<div data-note-id="teoria/interruzioni-ed-eccezioni/interruzioni">

## Interrupts

**Asynchronous hardware** signals travelling on the **control lines** of the bus, generated by external devices. They are asynchronous in the sense that they arrive at an instant unrelated to the running program.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/che-cosa-succede-nell-ordine">

## What happens, in order

1. The device raises the request line.
2. The processor completes the **current** instruction — it does not interrupt it halfway.
3. It saves the **state**: PC and status register, plus the registers the routine will use.
4. It disables (or lowers) interrupts at the same level, so as not to be interrupted right away.
5. It loads the address of the **ISR** (Interrupt Service Routine) into the PC and executes it.
6. It sends the acknowledgement to the device, restores the state and resumes from the next instruction.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/priorita-e-annidamento">

## Priority and nesting

With several devices an order is needed. Each source is assigned a **priority level**: a more urgent request can interrupt an ISR in progress (**nesting**), a less urgent one waits. The processor keeps a current level and accepts only higher requests. Interrupts can also be **masked** individually.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/come-si-individua-chi-ha-chiamato">

## How the caller is identified

- **Polling**: the processor queries the devices in sequence until it finds the one that raised the request. Simple, but the time grows with the number of devices.
- **Vectoring**: the device puts an identifier on the bus, which the processor uses to index a **vector table** and jump directly to the right ISR. Faster and independent of the number of devices.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/eccezioni">

## Exceptions

**Synchronous** events, generated by the processor during execution: division by zero, overflow, illegal opcode, protection violation, system calls. Synchronous because reproducible — re-running the same program on the same data they show up at the same point.

An exception is raised, for example, if a process tries to access the memory of other users, to change the system mode or the priority of other processes.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/interruzioni-vs-eccezioni-in-breve">

## Interrupts vs exceptions, in short

```
                interrupt           exception
origin          external device     processor
synchrony       asynchronous        synchronous
reproducible    no                  yes
typical use     I/O, timer          errors, system call
```

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/il-debugger">

## The debugger

- **Trace mode**: an exception after **every** instruction → step-by-step execution, the state is inspected at every step.
- **Breakpoint**: the exception fires only at chosen points → the program runs at full speed until the next one.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/i-o-programmato-e-dma">

## Programmed I/O and DMA

In **programmed** I/O the processor transfers every word itself: simple but wasteful of CPU time. With **DMA** (Direct Memory Access) a dedicated controller moves whole blocks between device and memory **without** the processor, which receives a single interrupt when the transfer completes. It is the mechanism by which a disk is read without paralysing the machine.

</div>

<div data-note-id="teoria/interruzioni-ed-eccezioni/bus-e-buffer">

## Buses and buffers

A bus carries **data, addresses and control signals**. When two devices work at different speeds a **buffer** is placed between them, compensating for the gap by accumulating the data. Transmission can be **parallel** (several bits together, short distance) or **serial** (one bit at a time, like USB: fewer wires, less interference, longer distances).

Interrupts are essential in **real-time** systems, where an event must be served within a maximum time, and in **multitasking** systems, where the timer that paces the context switches is itself an interrupt source.

</div>

## Worked example

**Two devices call, with different priorities.** The main program is running; the disk (priority 2) asks for attention, and while its routine is in progress the timer arrives (priority 5, higher):

```
t₀  main program running
t₁  disk request (p2)      → finishes the current instruction,
                             saves PC and status, masks ≤ 2, jumps to ISR_disk
t₂  ISR_disk running
t₃  timer request (p5)     → 5 > 2, so it is accepted:
                             saves PC and status of ISR_disk, jumps to ISR_timer
t₄  ISR_timer ends         → restores and returns into ISR_disk
t₅  ISR_disk ends          → restores and returns to the main program
```

Two points to note. The interrupt is served **between** two instructions, never halfway: the processor completes the current one. And nesting is allowed only upwards: if at time t₃ another priority-2 device had called, it would have waited because the mask excludes it.

</div>

## Common mistakes

- Saying that the interrupt “stops the instruction halfway”: it is served at the boundary between two instructions, which is what makes it possible to resume exactly where you were.
- Forgetting that the ISR must **save the registers it uses**: the interrupted program must not notice anything.
- Confusing priority with order of arrival: the one with higher priority goes first even if it asked later.
